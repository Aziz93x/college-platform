# ADR-0009: Sign-in, sessions and the authorization core

- Status: accepted
- Date: 2026-10-21
- Source: docs/PLAN.md, Step 6 (with its notes from Steps 4 and 5 and from ADR-0008); section 4, the login page
- Builds on: ADR-0001 (Better Auth, next-safe-action), ADR-0008 (no passkeys, no Entra provider, limits per account and address)

## Context

Step 6 puts sign-in at `/`: employee number or email, a password policy, lockout and idle timeouts from settings, "remember this device", two-factor for admins, a forced change after a temporary password, an admin's reset without email, `pnpm admin:create`, Secure host-only cookies, origin checks on every change, security headers and a nonce-based Content Security Policy. The college's limits are settings that change at run time, and Better Auth reads its options once.

## Decision

1. **Better Auth runs inside the server only.** Its HTTP routes are not mounted: the login, code, setup and password pages post to next-safe-action actions, which call `auth.api.*`. Every sign-in therefore passes the platform's own lockout and limits, and the only way in is a server action, whose origin Next.js checks. Better Auth's own rate limit and telemetry are off.
2. **People and accounts.** Better Auth's tables (`users`, `sessions`, `accounts`, `verifications`, `two_factors`) take ids from the database (`uuidv7()`); `people` gives each user a college and an employee number, unique per college. Someone signs in with either. An employee number typed in Arabic-Indic digits is read as Latin, an email in any case.
3. **Lockout and limits.** Attempts count against what was typed, an email or an employee number, with or without an account (`lockout.ts`, the `sign_in_lockouts` table). `auth.lockoutThreshold` attempts within `auth.lockoutMinutes` of the first, from any address, lock it for `auth.lockoutMinutes` from the one that reached the threshold. Each attempt is counted, in one statement, before its password is checked, so attempts that race each other cannot get past the threshold, and a sign-in clears the counts of both of the account's identifiers. An account's email and employee number therefore count apart, exactly as two identifiers with no account do. An unknown account gets the same answers as a wrong password, the lock included, and no answer links one identifier to the other. It also takes about as long: the platform hashes the typed password, while a real account goes through Better Auth's check, a few milliseconds slower in the second pass's measurement. The lockout leaves five timed attempts per identifier in each window, far too few to tell that apart through a network. (Amended after Audit 2, docs/reviews/audit-06.md: the count used to live on the account and never lapsed, so only real accounts locked.) Attempts are also limited per identifier and address in a window (`auth.signInAttempts`, `auth.signInWindowMinutes`); only failures count. The address is the first `X-Forwarded-For` entry: Caddy replaces a client's own, and Next.js fills it from the socket when nothing in front set it.
4. **Sessions follow the settings.** Better Auth gives every session the longest life a remembered device may have (90 days) and never refreshes it. On each request `getSessionUser()` applies the college's settings: a remembered device for `auth.rememberedDeviceDays` (30 by default), any other session for `auth.sessionHours` (12) and after `auth.idleMinutes` (60) without a request. A session past them is deleted, so its cookie signs nobody in. `remembered` is a column of the session; `last_seen_at` is written at most once a minute. The cookie is `__Secure-college.session_token`: host-only, Secure (localhost included), HttpOnly and SameSite=Lax, with an expiry only on a remembered device, so a shared browser forgets the others when it closes.
5. **Two-factor for admin powers.** A permission key says whether holding it requires two-factor; the system role holds them all. Whoever holds one sets up TOTP before anything else (`requireViewer()` sends them to `/two-factor/setup`): the password again, then the app's QR code or its key, ten backup codes shown once, and the first code. Secrets and backup codes are encrypted with `AUTH_SECRET`, which signs the cookies too: changing it signs everyone out and makes every two-factor secret unreadable.
6. **The authorization core.** Permission keys live in code (`src/modules/access/domain/permissions.ts`), roles and their keys in the database. `authorize(actor, permission, scope)` is pure, and three action clients carry it: `publicAction` (signing in), `signedInAction` (a session with something still pending: a password to replace, two-factor to set up, signing out) and `viewerAction`, which refuses a pending viewer and, when the action names a permission, a viewer who does not hold it in the scope's college. Each service writes its audit event inside its own transaction.
7. **Re-authentication before sensitive actions.** In this step the sensitive actions are changing the password and setting up two-factor, and both ask for the password again. The general step, confirming the password before an admin changes access, accounts or the sign-in settings, arrives with its first consumer in Step 7 (`auth.*` settings), then Steps 9 and 10 (docs/PLAN.md, notes from Step 6).
8. **Resets without email, and the first admin.** An admin's reset gives a temporary password (twelve characters from an alphabet without look-alikes, about 59 bits), shown once and never logged or audited, which ends every session of that person, lifts a lockout and must be replaced at the next sign-in; Step 10 gives it a screen. `pnpm admin:create` makes the first holder of the system role the same way and refuses once the role has a member, so the terminal is no way around the admins.
9. **A full page load after sign-in and sign-out.** With Cache Components, Next.js keeps the pages visited before, hidden, in the document and in its router cache. After signing in or out, setting up two-factor or changing the password, the forms load the next page from scratch, so no password, key or previous person's page stays in the browser.
10. **Headers.** `next.config.ts` sends `nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`, a Permissions-Policy, and same-origin opener and resource policies with every response, static files included. `src/proxy.ts` gives every page a Content Security Policy with a new nonce, which Next.js puts on its scripts (`'strict-dynamic'`, `'unsafe-eval'` only in development, `upgrade-insecure-requests` only over HTTPS). Styles stay `'unsafe-inline'`: Motion and the image component set style attributes, which no nonce covers. The proxy also refuses any change (a method other than GET, HEAD and OPTIONS) whose `Origin` does not name the host the request came to, or that has no `Origin` at all, which Next.js lets through for server actions.
11. **The design catalog.** `/design` stays a laptop page (the proxy's 404 elsewhere) and also requires `design.view`. On a laptop the page refuses after `loading.tsx` has streamed, so the status is 200 either way: a signed-out request gets a redirect to the login page in the stream, and a viewer without the key gets the not-found page, as for an address that does not exist (corrected after Audit 2).

Not built: Better Auth's HTTP routes, sign-up, email resets, passkeys and the Entra provider (ADR-0008).

## Consequences

- `AUTH_SECRET` (32 characters or more) joins the required environment, in `.env.example`, `docker/.env.example`, the compose file and CI. Step 41 generates it into the local `.env` without printing it and keeps it across restarts.
- The cookies are Secure, so a phone reaches the platform through Caddy's HTTPS address, never plain HTTP on the network.
- Tests and tools sign in the demo accounts: the end-to-end setup project saves each role's state, and `pnpm lighthouse` measures Today with the demo trainer's session. The demo password and the demo admin's authenticator secret are published in `db/seed/demo/accounts.ts`, as demo data; `seed:demo` refuses production.
- Better Auth accepts a TOTP code again within its 90-second window, a remembered device's cookie lasts 90 days while the server ends its session at the setting, and failed sign-ins are audited only when they lock an account (docs/BACKLOG.md).
- Better Auth allows five codes per challenge and locks two-factor for 15 minutes after ten wrong codes in a row. These are library defaults, not settings, and the lock writes no audit event yet (the note under Step 11).
- Each of an account's two identifiers allows the threshold, so someone guessing a password gets twice the attempts in each window: ten every 15 minutes by default.
