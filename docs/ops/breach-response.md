# الاستجابة لحوادث البيانات

- الحالة: مسودة، يعتمدها مسؤول حماية البيانات، وتُجرَّب مرة قبل التشغيل الفعلي
- التاريخ: 21 أكتوبر 2026
- المرجع:
  - نظام حماية البيانات الشخصية، المادة 20، واللائحة التنفيذية، المادة 24.
  - الضابط 2-13-3-3 من الضوابط الأساسية للأمن السيبراني (ECC-2:2024).
  - `docs/privacy/data-protection.md` و ADR-0013.

هذا ما يُفعل عند أي حدث قد يكشف بيانات شخصية لمن لا يحق له، أو يغيّرها، أو يتلفها، أو يمنع الوصول إليها. يُقصد بـ«المرحلة» هنا مراحل هذا الدليل، وبـ«الخطوة» خطوات خطة البناء في `docs/PLAN.md`.

## متى تستخدم هذا الدليل

أمثلة:
- دخول شخص بحساب غيره، أو عملية في سجل التدقيق لم يُجرها صاحب الحساب.
- ضياع جهاز عليه جلسة مفتوحة لمدير النظام أو لرئيس قسم.
- خروج نسخة احتياطية أو الملف `docker/.env` من الخادم.
- رفع ملف فيه بيانات حقيقية إلى المستودع العام: تقرير من رايات، أو لقطة شاشة، أو تفريغ قاعدة بيانات.
- خلل يسمح لدور برؤية ما ليس له.
- تعطّل أو تلف يُفقد بيانات.

إن شككت، فعاملها حادثة. التبليغ المبكر لا يضر، والتأخير قد يضر.

| الدور | من | ماذا يفعل |
| --- | --- | --- |
| المسؤول التقني للتشغيل | [الاسم] | يحفظ الأدلة، ويحتوي الحادثة، ويصلح، ويوثّق |
| مسؤول حماية البيانات | [الاسم] | يقيّم الضرر، ويبلّغ سدايا والأشخاص المتأثرين، ويمسك سجل الحوادث |
| الأمن السيبراني في المؤسسة | [الإدارة] | يبلّغ الهيئة الوطنية للأمن السيبراني، ويساند التحقيق |

احفظ أرقام التواصل في الطوارئ في مكان خارج المنصة، لأن المنصة قد تكون معطّلة: [المكان].

## المواعيد

تبدأ المهلة من لحظة علم الجهة بالحادثة، لا من لحظة وقوعها. اكتب فورًا: الوقت، ومن أبلغ، وماذا رأى.

| متى | ماذا |
| --- | --- |
| فورًا | سجّل لحظة العلم، وأبلغ المسؤول التقني ومسؤول حماية البيانات |
| خلال ساعة | احفظ الأدلة (المرحلة 1)، ثم احتوِ الحادثة (المرحلة 2) |
| خلال 24 ساعة | قيّم: أي بيانات، وكم شخصًا، وهل الضرر محتمل (المرحلة 3) |
| قبل مرور 72 ساعة | بلّغ سدايا في كل حادثة تمس بيانات شخصية، ولو بدا الضرر غير محتمل. النظام اليوم يشترط احتمال الضرر، ومسودة تعديل اللائحة (أكتوبر 2026) تسقط هذا الشرط. يعتمد مسؤول حماية البيانات هذا الاختيار. |
| في المهلة التي يحددها إجراء المؤسسة | بلّغ الهيئة الوطنية للأمن السيبراني عبر إدارة الأمن السيبراني في المؤسسة |
| دون تأخير غير مبرر | أبلغ الأشخاص المتأثرين إن كان الضرر محتملًا |
| خلال أسبوعين | راجع الحادثة بعد انتهائها (المرحلة 7) |

## الأوامر

تفترض الأوامر النسخة التي يشغّلها `pnpm local:up`، واسم مشروعها `college`، وتُشغَّل من مجلد المشروع. على الخادم، استخدم اسم مشروعه وملف أسراره (القسم K من الخطة).

```sh
compose="docker compose -p college -f docker/compose.yml --env-file docker/.env"
sql() { $compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 "$@"' -- "$@"; }
```

لمعرفة معرّف مستخدم من بريده أو رقمه الوظيفي:

```sh
sql -c "select u.id, u.name from users u join people p on p.user_id = u.id where u.email = lower('[البريد]') or p.employee_number = '[الرقم الوظيفي]'"
```

## المرحلة 1: احفظ الأدلة قبل أي تغيير

تُكتب الملفات في مجلد خارج المشروع، لأن فيها بيانات شخصية، والمستودع عام.

```sh
stamp=$(date +%Y%m%d-%H%M)
out="$HOME/incident-$stamp"
mkdir -p "$out" && chmod 700 "$out"
# نسخة من قاعدة البيانات الآن، خارج دورة النسخ الاحتياطية اليومية
$compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > "$out/database.dump"
# سجلات الحاويات
$compose logs --no-color --timestamps > "$out/logs.txt"
# سجل التدقيق في آخر 14 يومًا
sql --csv -c "select * from audit_events where created_at > now() - interval '14 days' order by created_at" > "$out/audit.csv"
```

- **بعدها:** انقل المجلد مشفّرًا إلى المكان الذي يحدده مسؤول حماية البيانات، ثم احذفه من الجهاز.
- **مدة النسخ اليومية:** تُحذف بعد نحو 15 يومًا. إن احتجت نسخة سابقة للمقارنة، فانسخها الآن قبل أن تُحذف.

## المرحلة 2: احتوِ الحادثة

اختر ما يناسب الحادثة. الأسرع أولًا.

### حساب واحد

الترتيب مهم: أوقف الحساب أولًا، ثم أعد تعيين كلمة المرور قبل أي تغيير في التحقق بخطوتين، حتى لا يدخل بها من يعرفها.

1. **أوقف الحساب** من شاشة الأشخاص (الخطوة 10 من الخطة). يخرج من كل جلساته فورًا، ولا يدخل به أحد حتى يُفعَّل من جديد.
   - لا يُوقَف حسابك أنت، ولا حساب مدير النظام الأخير. في هاتين الحالتين **أوقف المنصة** (انظر «إيقاف المنصة» أدناه).
2. **أعد تعيين كلمة المرور** من الشاشة نفسها. إعادة التعيين تُنهي كل جلسات الحساب، وتفكّ قفله، وتُلزم صاحبه بكلمة مرور جديدة عند الدخول.
3. **إن شككت في تطبيق المصادقة على جوال صاحب الحساب،** فأوقف تحققه بخطوتين من صفحته («إيقاف التحقق بخطوتين»، ADR-0014). بعدها يطلب منه الدخول التالي كلمة المرور المؤقتة، ثم إعداد التطبيق من جديد إن كانت الكلية تطلبه.
4. **فعّل الحساب من جديد** بعد التحقق، وسلّم صاحبه كلمة المرور المؤقتة بنفسك. وإن كنت أوقفت المنصة، فأعد تشغيلها بـ `pnpm local:up`.

إن اعتُمد ADR-0013، يحذف إيقاف الحساب كلمة مروره ومفتاح تحققه أيضًا، فلا تلزم الخطوة 3. وفي نسخة العرض تكفي إعادة إنشاء بياناتها.

### كل الجلسات

```sh
sql -c "delete from sessions"
```

- **الأثر:** يخرج الجميع، ويدخلون من جديد بكلمات مرورهم.
- **ما لا يتغير:** كلمات المرور والتحقق بخطوتين.
- **متى:** عند ضياع جهاز لا تعرف حسابه، أو اشتباه في جلسات مسروقة.

### إيقاف المنصة

```sh
$compose stop app worker
```

- **ما يبقى:** Caddy وقاعدة البيانات يعملان، فتبقى الأدلة.
- **ما يراه الناس:** المنصة لا تجيب، إلى أن تُعيد التشغيل بـ `pnpm local:up`.

### تسرّب الملف `docker/.env`

في هذا الملف `AUTH_SECRET` وكلمات مرور قاعدة البيانات.

1. **أوقف المنصة** كما في الفقرة السابقة.
2. **سرّ جديد:** امسح قيمة `AUTH_SECRET` في الملف. يكتب `pnpm local:up` قيمة جديدة لا يطبعها، فيخرج الجميع، ويصبح كل سرّ للتحقق بخطوتين غير مقروء (ADR-0009).
3. **التحقق بخطوتين:** احذفه للجميع. يعيد إعداده عند دخوله التالي من تطلبه الكلية منه، ومن شاء من الباقين من ملفه (ADR-0014):

   ```sh
   sql -c "begin" -c "delete from two_factors" -c "update users set two_factor_enabled = false" -c "commit"
   ```

   أعد قبل ذلك تعيين كلمات مرور من يملكون صلاحيات إدارية، إن احتمل أن تكون معروفة.
4. **كلمتا مرور قاعدة البيانات:**
   - غيّر كلمة مرور `POSTGRES_USER` بـ `alter role`، واكتب القيمة الجديدة نفسها في الملف.
   - كلمة مرور `APP_DATABASE_USER` تتبع الملف عند كل تشغيل (`db/migrate.ts`)، فيكفي تغييرها في الملف.
5. **أعد التشغيل** بـ `pnpm local:up`، فلا يسري شيء مما سبق قبله.

قاعدة البيانات لا تنشر منفذًا خارج شبكة Docker، لكن لا تؤجّل هذه المرحلة.

### بيانات حقيقية في المستودع العام

1. **اجعل المستودع خاصًا فورًا:** يفعلها مالكه على GitHub، من الإعدادات.
2. **احذف الملف من كامل التاريخ:** بـ `git filter-repo`، ثم ادفع التاريخ الجديد بـ `git push --force`. الحذف في commit جديد لا يكفي، لأن الملف يبقى في التاريخ.
3. **اطلب من دعم GitHub:** إزالة النسخ المخزّنة ومراجع طلبات الدمج.
4. **افترض أن الملف نُسخ:** قد يكون في نسخة متفرعة (fork) أو عند أحد، فقيّمه حادثةً كاملة.

## المرحلة 3: قيّم الحادثة

- **أي بيانات:** ارجع إلى جدول البيانات في `docs/privacy/data-protection.md`.
- **لمن، وكم شخصًا:** موظفون أو متدربون.
- **الضرر المحتمل:**
  - انتحال شخصية أو دخول بحساب غيره.
  - كشف أسئلة اختبار قبل موعده.
  - إحراج متدرب بغيابه أو درجته.
  - تغيير سجلات عمل.
- **هل كانت البيانات محمية:**
  - كلمات المرور مخزّنة بتجزئة باتجاه واحد.
  - أسرار التحقق مشفّرة بـ `AUTH_SECRET`، فإن خرج الملف `docker/.env` معها فهي مكشوفة.
- **من وصل، ومتى:** راجع سجل التدقيق وسجلات الحاويات.
- **هل ما زالت مستمرة.**

دوّن ما وصلت إليه، ولو ناقصًا.

## المرحلة 4: بلّغ

### سدايا

يبلّغ مسؤول حماية البيانات عبر منصة حوكمة البيانات الوطنية. الدخول إليها يحتاج رقم هوية وطنية أو إقامة.

البلاغ يتضمن:
- وصف الحادثة، ووقتها، وكيف وقعت.
- متى علمت الجهة بها.
- فئات البيانات وأنواعها.
- فئات الأشخاص المتأثرين وعددهم.
- عواقبها المحتملة.
- ما اتُّخذ وما سيُتخذ لاحتوائها.
- هل أُبلغ الأشخاص المتأثرون.
- وسيلة التواصل مع مسؤول حماية البيانات.

لا تؤخّر البلاغ حتى تكتمل المعلومات.

### الهيئة الوطنية للأمن السيبراني

عبر إدارة الأمن السيبراني في المؤسسة، وفق إجرائها للحوادث ومهلته (الضابط 2-13-3-3).

### الأشخاص المتأثرون

دون تأخير غير مبرر، إن كان الضرر محتملًا، بلغة واضحة وبسيطة. الرسالة تتضمن:
- ما حدث.
- أي بيانات تأثرت.
- ما فعلناه.
- ما يمكنهم فعله.
- وسيلة التواصل مع مسؤول حماية البيانات.

القناة:
- **للموظفين:** إشعار داخل المنصة، وبريد رسمي من الكلية.
- **للمتدربين:** قناة الكلية المعتادة معهم.

نموذج:

> تعرّضت منصة الكلية في [التاريخ] لـ[وصف مختصر]. قد تكون البيانات التالية تأثرت: [البيانات]. أوقفنا [ما أوقفناه]، و[ما فعلناه]. ننصحك بـ[ما يفعله، مثل تغيير كلمة المرور]. للاستفسار: مسؤول حماية البيانات، [وسيلة التواصل].

## المرحلة 5: أصلح واستعد

- **السبب:** أغلقه قبل إعادة التشغيل.
- **إن تغيّرت بيانات:** استعدها من آخر نسخة سليمة. استعدها أولًا في قاعدة منفصلة وتحقق منها، ثم استبدل بها قاعدة البيانات الحالية. الخطوة 42 من الخطة تضيف سكربت استعادة.
- **التحقق قبل الفتح:** شغّل الاختبارات، ومنها مصفوفة الصلاحيات (`tests/unit/permission-matrix.test.ts`).
- **الأسرار:** إن بقي شك فيها، فغيّرها كما في المرحلة 2.

## المرحلة 6: سجل الحوادث

تُسجَّل كل حادثة، حتى التي لم تستوجب تبليغًا. يمسك مسؤول حماية البيانات السجل خارج المنصة، ويحتفظ معه بنسخة من كل بلاغ وبما يثبت الإجراءات التصحيحية.

| الحقل | مثال |
| --- | --- |
| رقم الحادثة | 2026-01 |
| لحظة العلم، ولحظة الوقوع إن عُرفت | |
| الوصف | |
| البيانات المتأثرة وعدد الأشخاص | |
| الضرر المحتمل | |
| الإجراءات وتواريخها | |
| تبليغ سدايا: متى، أو لماذا لم يُبلَّغ | |
| تبليغ الأشخاص: متى وكيف، أو لماذا لم يُبلَّغوا | |
| تبليغ الهيئة الوطنية للأمن السيبراني | |
| الدروس، وما تغيّر بعدها | |

## المرحلة 7: بعد الحادثة

خلال أسبوعين من انتهائها:
- **المراجعة:** ما الذي حدث، ولماذا لم يُمنع، وكم استغرقت كل مرحلة.
- **اختبار للسبب:** يُكتب له اختبار يفشل لو أُزيل الإصلاح، كما تشترط قواعد المشروع في CLAUDE.md.
- **التحديث:** يُحدَّث هذا الدليل والملف `docs/privacy/data-protection.md` بما تعلّمناه.

## تمرين قبل التشغيل الفعلي

قبل دخول أول مدرب حقيقي، جرّب الدليل مرة على الورق بسيناريو واحد. مثلًا: ضاع جوال رئيس قسم، وعليه جلسة على جهاز اختار صاحبه تذكّره.

- **مَن يحضر:** الأدوار الأربعة.
- **ما يُسجَّل:** كم استغرق الاحتواء والتقييم.
- **النتيجة:** ما يحتاج تعديلًا في الدليل.

يُضاف التمرين إلى قائمة ما قبل التشغيل في القسم 7 من الخطة.
